## Problem Statement

当前前端已经安装 HeroUI，但基础控件仍处于混用状态：部分弹窗和进度条使用 HeroUI，其他业务面板继续使用原生按钮、输入框、选择框、文本域和手写控件样式。随着学习路线、复习、测验、资料库、RAG 问答和模型配置继续增加，基础控件的外观、焦点状态、禁用状态、错误状态和响应式行为需要在多个模块中重复维护。

当前前端已有主题状态模块、主题持久化、首屏主题初始化和侧栏切换入口，但主题样式只覆盖部分页面，缺少一套明确的验证方式来确认所有业务面板及 HeroUI 控件在两种主题下都能保持一致的可读性、状态反馈和交互行为。本任务应完善现有主题能力，而非新增第二套主题系统。

## Solution

继续使用已经接入项目的 HeroUI 作为前端基础界面框架，统一管理按钮、输入框、文本域、选择器、Tabs、弹窗、Tooltip、进度和加载状态等通用控件。使用 Tailwind 和少量全局 CSS 管理页面布局、业务内容、响应式规则和主题变量，不再为基础控件重复实现一套平行样式。

完善现有浅色/深色模式切换能力，切换入口使用 HeroUI 控件，并让同一主题状态驱动 HeroUI 的浅色/深色样式。所有迁移范围内的 HeroUI 控件都必须在浅色和深色模式下完成交互验证，包括通过 portal 渲染的弹窗、选择器浮层和 Tooltip。HeroUI 的深色组件通过主题机制切换，无需为浅色和深色维护两套控件。未来课堂白板属于独立业务模块，可接入专用白板或画布引擎；本任务不实现白板，也不提前把白板交互抽象进基础界面层。

## User Stories

1. 作为学习者，我希望所有页面的常用按钮具有统一的外观和交互反馈，以便不需要重新理解每个页面的控件。
2. 作为学习者，我希望所有输入框、文本域和选择器具有统一的焦点、禁用、错误和占位状态，以便能清楚知道当前可以进行什么操作。
3. 作为学习者，我希望可以在浅色模式和深色模式之间切换，以便根据环境选择舒适的学习界面。
4. 作为学习者，我希望切换主题后当前页面的内容和控件立即保持可用，以便不需要刷新页面或重新打开当前功能。
5. 作为学习者，我希望重新打开应用后保留上一次选择的主题，以便不需要每次重复设置。
6. 作为学习者，我希望在深色模式下仍能清楚阅读表单文字、辅助文字、错误提示、进度信息和业务内容，以便长时间学习。
7. 作为学习者，我希望弹窗在浅色和深色模式下都具有清晰的背景、边界、标题层级和关闭操作，以便安全编辑或删除项目。
8. 作为学习者，我希望项目侧栏在两种主题下都能清楚区分当前项目、普通项目、加载状态和错误状态，以便快速切换项目。
9. 作为学习者，我希望工作区 Tabs 在两种主题下都能清楚显示当前标签，并保持键盘和鼠标切换能力。
10. 作为学习者，我希望学习路线中的节点状态控件在两种主题下都能区分待开始、学习中、已掌握和需复习等状态，以便准确维护学习进度。
11. 作为学习者，我希望路线创建表单在生成预览、调整路线、保存项目和启动内容准备期间正确禁用相关控件，以便避免重复提交。
12. 作为学习者，我希望路线创建表单在两种主题下都能清楚显示错误、进度和后台准备状态，以便知道下一步如何处理。
13. 作为学习者，我希望节点详情中的生成课程、生成实操、拉取资料和保存笔记操作具有统一的加载和禁用反馈，以便知道操作是否正在执行。
14. 作为学习者，我希望复习面板中的查看答案、评分和刷新操作在两种主题下都保持清晰可辨，以便连续完成复习。
15. 作为学习者，我希望测验面板中的知识点选择、题型选择、答案输入和提交操作使用统一的基础控件，以便专注于答题内容。
16. 作为学习者，我希望测验的正确、错误、掌握度和下一题反馈在两种主题下具有足够的颜色对比度和文本说明，以便理解反馈。
17. 作为学习者，我希望资料库中的知识点选择、文件选择、上传、索引进度和删除确认操作在两种主题下都能正常使用。
18. 作为学习者，我希望删除资料或项目时仍然需要明确输入确认词，并且在删除进行期间不能重复提交或误关闭操作。
19. 作为学习者，我希望 RAG 问答中的资料范围选择、资料复选、提问、停止和重试操作使用统一的基础控件，以便清楚控制当前问答范围。
20. 作为学习者，我希望 RAG 流式回答、引用资料、错误提示和读取状态在两种主题下都能保持可读，以便持续跟踪回答过程。
21. 作为学习者，我希望模型配置中的档案选择、文本输入、API Key 输入、连接测试、保存和删除操作使用统一控件，以便安全维护模型配置。
22. 作为学习者，我希望模型配置中“已就绪”和“未配置”等状态在两种主题下都能清楚识别，以便判断模型是否可以使用。
23. 作为维护者，我希望基础控件主要由 HeroUI 提供，以便修复或调整通用交互时减少跨业务模块的重复修改。
24. 作为维护者，我希望业务模块继续持有自己的异步状态和领域行为，以便 UI 框架迁移不会改变 API 契约和学习业务逻辑。
25. 作为维护者，我希望只为重复出现且有稳定语义的组合创建少量共享模块，以便避免为每个 HeroUI 控件增加无意义的转发包装层。
26. 作为维护者，我希望能通过一次主题验收清单确认所有迁移范围内的控件都经过浅色和深色验证，以便防止新增控件只在单一主题下可用。
27. 作为维护者，我希望未来可以将课堂白板作为独立业务模块接入专用渲染或白板引擎，以便白板的复杂交互不会迫使整个基础控件体系更换框架。
28. 作为学习者，我希望学习看板的刷新、导出和状态反馈遵循同一套控件与主题规范，以便查看和导出学习记录。
29. 作为维护者，我希望每项基础控件都有明确的 HeroUI 对应实现或合理例外，以便验证接入范围，而不是根据页面是否变暗判断迁移完成。

## Implementation Decisions

- 保留 HeroUI 作为唯一的基础界面组件框架，不引入 shadcn/ui 或另一套完整组件库。
- 直接使用 HeroUI 提供的基础控件；只有在多个业务模块拥有相同语义和相同交互时，才增加共享组合模块，例如带 Tooltip 的图标按钮或带业务标签的选择器。
- 不建立可切换 HeroUI、shadcn/ui 或其他框架的抽象层，不为每个基础控件建立只转发 props 的包装模块。
- 主题模块负责浅色、深色和系统主题的解析、持久化、DOM 主题状态切换，以及 HeroUI 所需主题状态的统一同步。
- 深色模式切换必须可从项目侧栏或现有全局可见位置触发，并提供明确的可访问名称和当前状态反馈。
- 首次加载时应尽量根据已保存主题同步主题状态，避免页面先显示错误主题再闪烁到目标主题。
- HeroUI 组件的主题样式作为基础控件默认实现；页面级 CSS 只负责布局、业务模块的层次、内容排版和确有必要的领域状态样式。
- 原生文件上传等具有明确浏览器语义、且不适合替换为 HeroUI 视觉控件的元素可以保留，但必须与周围 HeroUI 控件保持一致的布局、焦点和主题表现。
- 迁移范围包括项目侧栏、项目编辑和删除弹窗、工作区 Tabs 与进度、加载和错误状态、路线创建、路线列表、节点详情、状态控制、学习看板、复习、测验、资料库、RAG 问答和模型配置。
- 迁移只改变基础控件的渲染和样式来源，不改变业务状态所有权、请求函数、API DTO、错误处理语义、节点状态机和 SSE 数据流。
- 迁移后的控件必须保留提交中禁用、加载反馈、错误重试、确认删除、键盘焦点和可访问名称等既有行为。
- 工作区 Tabs 应使用 HeroUI Tabs 的选中状态和键盘交互；业务面板仍由工作区模块根据选中项渲染或保持必要状态。
- 下拉选择、复选、输入、文本域、按钮、弹窗、进度和加载状态应优先使用 HeroUI 对应实现，不再为这些基础控件继续扩大手写全局 CSS。
- 课堂白板不属于本次迁移范围。未来白板应在业务模块层形成独立接口，内部可选择 tldraw、Excalidraw 或其他专用引擎；白板周边的按钮、弹窗和设置控件继续使用 HeroUI。
- 组件验收需要建立主题矩阵：每个迁移模块至少在浅色模式和深色模式下检查默认、悬停、聚焦、禁用、加载、错误和已选状态中适用的状态。
- 主题验收以用户可见行为为准，不以 HeroUI 的内部 DOM 结构或内部 CSS 类名为测试契约。
- 控件接入审查与主题验收分别执行：静态检查确认控件来自 HeroUI、共享组合或已登记例外；浏览器检查确认这些控件在切换主题后保持正确视觉与交互。只导入 HeroUI、只更换标签、只增加深色 CSS 均不足以判定完成。
- 使用 HeroUI 的主题变量集中配置控件配色，不依赖逐页面覆写背景色模拟深色组件。业务内容区域也需要适配同一主题，避免库控件变暗而课程、卡片或提示区域仍保持浅色。

## Testing Decisions

- 测试以用户通过页面完成的行为为主，跨越业务模块对外接口；不测试 HeroUI 内部实现、内部 DOM 结构或内部 CSS 类名。
- 在 API 客户端请求处模拟后端返回，真实渲染迁移后的 HeroUI 控件，以便同时验证业务状态和控件的可操作性。
- 延续现有 Vitest、Testing Library、user-event 和 jsdom 测试方式，覆盖项目切换、项目编辑、项目删除、工作区 Tabs 和路线节点详情等已有行为。
- 增加主题行为测试：切换浅色/深色模式后，根主题状态更新、切换按钮可访问名称更新、主题偏好保存，并且当前业务视图仍然存在。
- 增加基础控件行为测试：Tabs 切换和键盘操作、选择器选中、输入控件禁用、按钮加载禁用、弹窗关闭限制、确认词校验和错误提示。
- 增加业务模块状态测试：路线生成和保存、节点详情操作、复习评分、测验提交、资料上传与删除、RAG 提问和停止、模型配置保存与连接测试。
- 对每个迁移模块至少提供一个浅色/深色主题验收场景。jsdom 负责验证主题状态和可访问交互；真实浏览器验收负责检查颜色对比度、浮层位置、滚动和视觉可读性。
- 测试必须覆盖窄屏布局、长文本、加载中、失败重试和操作进行中的禁用状态。
- 完成标准包括前端类型检查、全部前端测试和 Next.js 静态生产构建通过。
- 不为每个控件编写重复的浅色/深色 jsdom 测试；主题状态行为集中验证，业务面板测试覆盖实际迁移风险，视觉验收使用真实浏览器。

### 接入与主题验收矩阵

实施时记录每一行的实际 HeroUI 控件、保留原生元素及理由，以及浅色、深色、主题往返切换的验证结果。以下为验收计划，不代表已经验证通过。

| 模块 | 基础控件与内容 | 必须覆盖的主题与交互场景 |
| --- | --- | --- |
| 全局主题与应用外壳 | HeroUI 切换按钮、页面背景、文字 | 浅色→深色→浅色，刷新后恢复偏好，系统主题已有行为保持兼容，切换不丢失项目与输入 |
| 项目侧栏 | 选择、刷新、新建、编辑、删除、进度 | 当前项目、普通项目、空列表、加载、错误、焦点 |
| 项目弹窗 | Modal、Input、TextArea、Button | 打开后切换主题，遮罩与正文、校验、提交中禁用及关闭限制、删除确认词 |
| 工作区 | Tabs、ProgressBar、加载和状态控件 | 鼠标与键盘切换、选中态、焦点、路线详情必要状态保留 |
| 路线创建 | 输入、文本域、数字输入、操作按钮 | 预览、调整、保存、准备任务、失败重试与禁用态 |
| 路线列表与节点详情 | 节点入口、状态按钮、笔记与生成操作 | 已选/禁用状态、课程 Markdown、代码、表格、参考链接、错误反馈 |
| 学习看板 | 刷新、导出、统计与热力图 | 加载、错误、数据文本和热力值在两种主题下可辨 |
| 到期复习 | 查看答案、评分、刷新 | 正反面内容、评分操作、空队列、错误 |
| 查漏测验 | Select、Input、TextArea、选项和提交按钮 | 浮层与长选项、已选答案、提交禁用、正确和错误反馈 |
| 资料库 | Select、上传、刷新、删除与确认输入 | 文件输入例外、索引进度、失败、确认删除、浮层 |
| RAG 问答 | Select、Checkbox、TextArea、操作按钮 | 资料勾选、流式回答、引用、停止、重试、浮层和禁用态 |
| 模型配置 | Select、Input、密码输入和操作按钮 | 档案选择浮层、保存、连接测试、就绪状态、错误 |

### 完成标准

1. 全局可见位置提供基于 HeroUI 的浅色/深色切换入口；它驱动现有统一主题状态，偏好可持久化。
2. 迁移范围内每一种基础控件都有明确的 HeroUI 来源；保留的原生元素在验收记录中列明用途和理由。
3. 各业务模块均完成浅色、深色和往返切换验收；通过 portal 渲染的浮层、弹窗、Tooltip 与当前主题一致。
4. 默认、悬停、键盘焦点、禁用、加载、错误、选中等适用状态清晰可辨，不以颜色作为唯一状态说明。
5. 主题切换不重置当前项目、功能标签、笔记草稿、表单输入、问答记录或中断正在进行的操作。
6. 无为基础控件保留的重复手写皮肤或废弃控件规则；业务排版和已登记例外可以继续使用 CSS。
7. 用户行为测试、类型检查、静态构建与真实浏览器验收通过，附控件来源记录与双主题验证证据。

## Out of Scope

- 不引入 shadcn/ui、Material UI、Ant Design 或其他完整基础组件库。
- 不重写 React、Next.js、Tailwind、API 客户端或后端架构。
- 不修改 FastAPI 路由、学习业务服务、数据库模型、API DTO、SSE 协议或模型配置协议。
- 不重做产品品牌、页面信息架构或学习业务流程。
- 不实现课堂白板、画布编辑器、自由绘图、拖拽连线、白板对象协议或 AI 讲课步骤协议。
- 不在本任务中选择或引入 tldraw、Excalidraw 等白板引擎。
- 不建立所有 HeroUI 组件的项目级二次封装，也不追求消除每一个原生 HTML 元素。
- 不将业务组件改造成通用设计系统组件。

## Further Notes

当前仓库已安装 HeroUI 3 和 HeroUI styles，且部分弹窗、进度和状态页面已经使用 HeroUI。当前已停止代码实施；工作区中 12 个现有模块和 2 个新增共享组合包含尚未完成验证的临时迁移改动。这些改动没有提交，不是本任务的完成结果。重新获得实施授权后，先审阅并整理这些改动；不执行整仓回退，不覆盖其他未提交工作。

实施阶段：

1. 基线与盘点：确认既有业务行为，完成基础控件来源清单、原生元素例外和主题验收计划。
2. 统一主题与核心交互：完善现有主题同步，完成侧栏、项目弹窗、Tabs 和进度的完整交互迁移与验证。
3. 按业务模块迁移：路线与详情、看板、复习、测验、资料、问答、配置逐项完成控件接入和双主题验收。
4. 清理与交付：清理重复控件样式，更新开发约定，完成测试、类型检查、静态导出和浏览器验收记录。
